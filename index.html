네 가지 요소, 심화편

슬래시 커맨드 하나를 실행했는데 스킬이 로드되고, 도구 호출이 일어나고, MCP 서버가 응답합니다. 이 문서는 그 한 턴을 해부합니다. 파일을 어디에 어떤 형태로 두는지, GUI 어디에서 관리하는지, 슬래시 커맨드가 무엇인지, 그리고 이 전부를 코드로 묶는 하니스가 무엇을 조절하는지를 예시와 함께 다룹니다.

전제
기본편의 네 가지 개념을 읽었다고 가정합니다
분량
통독 25분, 필요한 절만 골라 읽는 구성입니다
기준
Anthropic, OpenAI, Google 공식 문서 (각 절 하단에 출처)

00시작하기 전에

기본편과 심화편의 경계

기본편은 네 가지가 각각 무엇인지를 다뤘습니다. 심화편은 그 네 가지가 실제 도구 안에서 어떻게 맞물려 도는지를 다룹니다.

이 문서가 답하는 질문은 다섯 개입니다.

  • 왜 한 턴에 전부 같이 도는가슬래시 커맨드, 스킬, 도구 호출, MCP가 같은 턴에 겹쳐 등장하는 구조를 그림으로 봅니다.
  • 파일은 어디에 어떤 형태로 두는가.claude 디렉터리의 실제 하이어라키와, 서브에이전트와 스킬과 커맨드의 형태 차이를 예시 코드로 봅니다.
  • GUI에서는 어디에 있는가Claude 데스크톱 앱 기준으로 네 요소 각각의 관리 화면 위치를 확인합니다.
  • 슬래시 커맨드란 무엇인가빌트인, 번들 스킬, 커스텀 세 종류를 구분하고 실행 메커니즘을 봅니다.
  • 하니스는 무엇을 조절하는가프롬프트, 컨텍스트, 하니스 엔지니어링의 관계와, md 파일만으로 가능한 범위를 확인합니다.

예시는 Claude Code와 Claude 데스크톱 앱 기준입니다. 다만 파일 규약의 핵심인 SKILL.md는 오픈 표준이라 OpenAI Codex CLI와 Google Gemini CLI도 같은 형식을 읽습니다. 05절에서 하니스별 차이를 표로 정리합니다.

01한 턴의 해부

네 가지가 한 턴에 같이 도는 이유

네 요소는 같은 자리를 두고 고르는 선택지처럼 보이지만 서로 다른 층의 부품입니다. 층이 다르기 때문에 한 턴 안에서 겹쳐 도는 것이 정상 동작입니다.

한 문장씩
슬래시 커맨드는 사람이 잡는 시작 손잡이입니다. 스킬은 그 손잡이가 대화에 밀어 넣는 프롬프트입니다. 도구 호출은 모델이 바깥으로 손을 뻗는 유일한 문법이고, MCP는 그 손이 닿는 외부 도구의 배선입니다. 서브에이전트는 이 전체가 별도 컨텍스트에서 한 번 더 도는 것입니다.

시간 순서로 펼치면

커스텀 커맨드 /fix-issue 123을 입력한 순간부터 답이 나올 때까지입니다. 1번은 사람이, 2번과 3번은 하니스가, 4번부터는 모델이 주도합니다.

도구 호출 한 번의 실제 모양

네 요소 중 도구 호출만 파일이 없습니다. API 요청과 응답에 들어가는 JSON이 실체의 전부입니다.

요청과 응답에 들어가는 세 조각
// 1. 요청에 도구를 정의합니다
"tools": [{
  "name": "get_weather",
  "description": "도시의 현재 날씨를 조회합니다",
  "input_schema": {
    "type": "object",
    "properties": { "city": { "type": "string" } },
    "required": ["city"]
  }
}]

// 2. 모델의 응답 (stop_reason: "tool_use")
{ "type": "tool_use", "name": "get_weather", "input": { "city": "Seoul" } }

// 3. 실행 결과를 다음 요청에 넣어 돌려보냅니다
{ "type": "tool_result", "content": "맑음, 31도" }

실행은 2와 3 사이, 모델 바깥에서 일어납니다. 이 왕복을 자동으로 돌려 주는 코드가 하니스입니다.

슬래시와 골뱅이 연결된 MCP 서버가 프롬프트를 내놓으면 /mcp__서버명__프롬프트명 형태의 슬래시 커맨드로 나타납니다. 스킬은 /스킬이름으로 부르고, 서브에이전트만 @agent-이름이라는 별도 문법으로 부릅니다.

02파일 규약

.claude 디렉터리의 실제 하이어라키

전부 .claude 폴더에 md로 넣는다는 통념은 절반만 맞습니다. 셋 다 md인 것은 맞지만 형태가 서로 다르고, md가 아닌 구성원이 오히려 동작을 강제합니다.

어디에 무엇을 두나 (사용자 스코프 + 프로젝트 스코프)
~                                홈 디렉터리
├── .claude/                     사용자 스코프: 모든 프로젝트에 적용
│   ├── CLAUDE.md                모든 세션에 들어가는 개인 지침
│   ├── settings.json            전역 권한과 훅
│   ├── agents/
│   │   └── reviewer.md          낱개 md 파일 하나 = 서브에이전트 하나
│   ├── skills/
│   │   └── deploy/
│   │       └── SKILL.md         폴더 하나 = 스킬 하나, 파일명 고정
│   └── commands/
│       └── fix-issue.md         낱개 md 파일 하나 = /fix-issue
├── .claude.json                 MCP 유저 스코프. 폴더처럼 보이지만 파일입니다
│
└── 프로젝트/
    ├── CLAUDE.md                팀 공유 사실, 커밋 대상
    ├── .mcp.json                MCP 프로젝트 스코프. .claude 밖 루트에 둡니다
    └── .claude/
        ├── settings.json        팀 공유 권한과 훅, 커밋 대상
        ├── settings.local.json  개인용, gitignore 대상
        ├── rules/
        │   └── swift-style.md   paths 조건으로 골라 적용되는 지침
        ├── agents/
        │   └── code-reviewer.md
        ├── skills/
        │   └── release-check/
        │       ├── SKILL.md
        │       ├── references/  읽을 때만 컨텍스트에 로드
        │       └── scripts/     실행만 되고 코드는 컨텍스트 밖
        └── commands/
            └── deploy.md        /deploy, 스킬과 같은 메커니즘

파란 글씨가 md(모델이 읽는 프롬프트)입니다. settings.json과 .mcp.json은 하니스가 파싱해 강제하는 설정이고, ~/.claude.json은 ~/.claude/ 폴더 밖, 홈 바로 아래에 놓인 파일이라 자주 헷갈립니다.

형태가 다른 세 가지

  • 서브에이전트는 낱개 md 파일입니다.claude/agents/이름.md. frontmatter의 name과 description 두 개만 필수이고, 파일명은 자유입니다. frontmatter가 아예 없으면 서브에이전트로 로드되지 않습니다.
  • 스킬은 폴더이고 파일명이 고정입니다.claude/skills/이름/SKILL.md. 폴더 하나가 스킬 하나이며, 진입 파일명은 반드시 SKILL.md로 고정입니다. 필수 필드는 없고 description만 권장입니다.
  • 커맨드는 낱개 md이고 스킬과 통합됐습니다.claude/commands/이름.md. frontmatter가 없어도 동작합니다. commands/deploy.md와 skills/deploy/SKILL.md는 똑같이 /deploy를 만들고, 이름이 겹치면 스킬이 이깁니다.

예시 1. 서브에이전트

.claude/agents/code-reviewer.md
---
name: code-reviewer
description: 코드 변경을 리뷰합니다. 수정 작업이 끝난 뒤에 사용하세요.
tools: Read, Grep, Glob
model: haiku
maxTurns: 15
---

너는 시니어 코드 리뷰어다.
변경된 파일을 읽고 문제를 심각도 순으로 보고한다.
직접 수정하지 말고 보고만 한다.

본문은 새로 뜨는 에이전트의 시스템 프롬프트가 됩니다. 그래서 2인칭 지시문으로 씁니다. description은 모델이 언제 위임할지 판단하는 근거입니다. tools로 도구를 좁히고 model로 경량모델을 지정해 비용을 줄입니다.

예시 2. 스킬

.claude/skills/release-check/SKILL.md
---
name: release-check
description: 배포 전 점검을 실행합니다. 릴리스, 배포, 출시 준비를 요청받으면 사용하세요.
---

## 순서
1. scripts/preflight.sh 를 실행하고 실패 항목을 보고한다.
2. references/checklist.md 의 항목을 순서대로 확인한다.
3. 전부 통과하면 결과를 표로 정리한다.

평소에는 name과 description 약 100토큰만 상주하고, 발동될 때 본문이 로드됩니다. references/ 문서는 읽는 시점에 컨텍스트로 들어오지만, scripts/ 코드는 실행만 되고 출력만 들어옵니다. 이 3단계가 점진적 공개입니다.

예시 3. 커스텀 커맨드

.claude/commands/fix-issue.md
---
description: GitHub 이슈를 수정합니다
argument-hint: [이슈 번호]
---

GitHub 이슈 $ARGUMENTS 를 우리 코딩 규칙에 맞게 수정하라.

현재 상태:
!`git status --short`

규칙 문서: @docs/CONTRIBUTING.md

/fix-issue 123을 치면 $ARGUMENTS가 123으로 치환되고, ! 줄은 셸 실행 결과로, @ 경로는 파일 내용으로 바뀐 뒤 대화에 주입됩니다.

예시 4. md가 아닌 두 파일

.mcp.json (프로젝트 루트, 커밋 대상)
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/"
    },
    "xcode": {
      "command": "xcrun",
      "args": ["mcpbridge"]
    }
  }
}

원격 서버는 url로, 로컬 서버는 command로 붙습니다. 팀원이 클론하면 같은 연결을 갖게 됩니다. Xcode 26.3부터는 Xcode 자체가 MCP 서버라서 xcrun mcpbridge로 연결합니다.

.claude/settings.json (권한과 훅)
{
  "permissions": {
    "allow": ["Bash(npm test:*)", "Read(**)"],
    "deny": ["Bash(rm -rf:*)", "Read(.env)"]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "swiftformat ." }]
      }
    ]
  }
}

파일을 고칠 때마다 포매터가 반드시 돕니다. md에 적은 지침은 확률적으로 지켜지지만, 여기 적은 규칙은 하니스가 예외 없이 실행합니다.

우선순위가 서로 반대입니다 같은 이름이 두 스코프에 있을 때, 서브에이전트는 프로젝트가 개인 설정을 이기고 스킬은 개인이 프로젝트를 이깁니다. 둘을 나란히 가르칠 때 걸리는 함정입니다. MCP는 로컬, 프로젝트, 유저 순서로 이깁니다.
이식성 주의 SKILL.md는 오픈 표준이라 여섯 필드(name, description, license, compatibility, metadata, allowed-tools)만 표준입니다. argument-hint 같은 Claude Code 전용 필드가 든 스킬을 claude.ai에 업로드하면 무시되지 않고 하드 에러가 납니다.
같은 md라도 본문의 역할이 다릅니다 스킬과 커맨드의 본문은 대화에 주입되는 프롬프트이고, 서브에이전트의 본문은 새로 뜨는 에이전트의 시스템 프롬프트입니다. 이것이 셋을 가르는 가장 깔끔한 기준입니다.

03데스크톱 앱

GUI에서는 어디에 있나

데스크톱 앱은 하나이고 그 안에 Chat, Cowork, Code 세 탭이 있습니다. Code 탭이 곧 Claude Code입니다. 네 요소가 GUI에 노출된 정도는 전부 다릅니다.

요소GUI 위치할 수 있는 것경계
스킬 사이드바 Customize의 Skills 목록 확인, 개별 켜고 끄기, zip 업로드로 내 스킬 추가. 엑셀, 워드, PPT, PDF 같은 기본 스킬도 같은 목록에 있습니다. 전제 조건으로 Settings의 Capabilities에서 코드 실행을 먼저 켜야 합니다.
MCP Customize의 Connectors 원격 서버를 이름과 URL로 추가. 서버가 내놓은 도구를 하나씩 켜고 끄고, 도구 권한을 항상 허용, 승인 필요, 차단 중에서 고릅니다. 커스텀 커넥터는 Anthropic 클라우드에서 접속하므로 localhost와 사내망 서버는 연결되지 않습니다. 로컬 서버는 아래 세 경로를 씁니다.
도구 호출 정의하는 화면이 없습니다 켜고 끄기만 가능합니다. 웹 검색은 입력창에서 대화 단위로, 코드 실행은 Settings의 Capabilities에서 계정 단위로 켭니다. 스키마를 직접 쓰는 자리는 API와 MCP뿐입니다.
서브에이전트 Chat 탭에는 없습니다 플러그인에 묶여 들어오지만 채팅에서는 비활성으로 표시되고, 실제 실행은 Cowork와 Code 탭에서만 됩니다. 파일로 정의하는 서브에이전트는 Claude Code 전용입니다.

로컬 MCP 서버를 붙이는 세 경로

  1. 패키지가 있다면 확장 설치Settings의 Extensions에서 .mcpb 번들을 설치합니다. 예전 .dxt가 이름을 바꾼 것으로, 압축 안의 manifest.json이 서버 정보를 선언합니다.
  2. 패키지가 없다면 설정 파일 직접 편집Settings의 Developer에서 Edit Config를 누르면 claude_desktop_config.json이 열립니다. 저장 후 앱을 완전히 종료했다가 다시 실행해야 반영됩니다.
  3. 공개 서버라면 원격 커넥터로서버를 인터넷에 올릴 수 있다면 Connectors에서 URL로 추가하는 편이 관리가 쉽습니다.
~/Library/Application Support/Claude/claude_desktop_config.json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/Desktop"]
    }
  }
}

macOS 경로 기준이며 Windows는 %APPDATA%\Claude\ 아래에 있습니다. 여기 정의한 서버는 Chat 탭과 로컬 Code 탭 세션 양쪽에서 쓸 수 있습니다.

플랜 기준 디렉터리에 등록된 기본 커넥터는 전 플랜에서 쓸 수 있고, 커스텀 커넥터는 무료 플랜에서 1개까지입니다. 스킬 zip 업로드는 개인 계정 단위이며, 플러그인은 유료 플랜 전용입니다. Team과 Enterprise는 조직 설정에서 소유자가 먼저 켜야 구성원에게 보입니다.

04슬래시 커맨드

슬래시 커맨드는 무엇인가

한 메뉴에 성격이 다른 세 종류가 섞여 있습니다. 실체는 저장된 프롬프트 템플릿과, 그것을 대화에 밀어 넣는 손잡이입니다.

종류실행 주체예시
빌트인CLI 코드가 직접 실행합니다. 모델에게 가지 않습니다./clear, /compact, /model, /resume, /permissions, /usage
번들 스킬모델에게 넘어가는 프롬프트입니다. 문서의 커맨드 표에서 [Skill] 표시로 구분합니다./code-review, /debug, /loop, /security-review
커스텀내가 만든 md 파일을 렌더링해 대화에 주입합니다./fix-issue, /deploy

커스텀 커맨드의 메커니즘

  1. 입력/fix-issue 123을 칩니다. 파일명이 커맨드 이름이 됩니다.
  2. 렌더링하니스가 파일을 열어 $ARGUMENTS를 인자로 치환하고, ! 줄을 셸로 실행해 출력으로 바꾸고, @ 경로를 파일 내용으로 인라인합니다.
  3. 주입렌더링된 텍스트가 사용자 쪽 메시지로 대화에 들어갑니다. 이후는 일반 턴과 같고, 주입된 내용은 세션이 끝날 때까지 남습니다.

파일에 "이슈 $ARGUMENTS 를 수정하라"라고 써 두고 /fix-issue 123을 치면, 모델이 실제로 받는 것은 "이슈 123 을 수정하라"입니다. 스킬을 /스킬이름으로 부를 때도 같은 일이 일어납니다.

발동 방향을 잠그는 두 필드

frontmatter사람이 /이름모델이 자동쓰는 경우
기본값가능가능설명이 항상 컨텍스트에 있어 모델이 알아서 로드합니다.
disable-model-invocation: true가능불가배포처럼 부작용이 있는 작업. 코드가 준비돼 보인다고 모델이 배포를 결정하면 안 되기 때문입니다.
user-invocable: false불가가능메뉴에는 숨기고 모델만 쓰는 내부 절차.
채팅 탭과의 차이 데스크톱 앱의 Chat 탭에서 슬래시를 치면 커넥터와 도구 메뉴가 열립니다. 채팅에서 스킬은 타이핑 없이 자동으로 발동하고, 슬래시 메뉴가 온전히 있는 곳은 Code 탭과 Cowork입니다.
다른 셋과의 차이 슬래시 커맨드는 네 요소 목록 밖에 있습니다. 사람이 그것들을 부르는 손잡이입니다. 커스텀 커맨드는 스킬과 같은 메커니즘으로 통합됐고, 서브에이전트만 @agent-이름이라는 별도 문법을 씁니다.

05하니스

하니스 엔지니어링이 조절하는 것

모델은 텍스트를 뱉을 뿐이고, 그것을 에이전트로 만드는 것은 전부 바깥 코드입니다. 그 코드 전체를 설계하는 일이 하니스 엔지니어링입니다.

코드단의 손잡이 열 가지

  • 루프 자체stop_reason이 tool_use인 동안 실행하고 다시 호출하는 while문, 최대 턴 수, 종료 조건, 실패 시 재시도.
  • 시스템 프롬프트 조립정적 지침에 작업 디렉터리, git 상태, 날짜, CLAUDE.md, 스킬 메타데이터 같은 동적 상태를 매 턴 합성합니다.
  • 도구 레지스트리와 게이팅어떤 도구를 어떤 스키마로 언제 노출할지. 도구가 많으면 전부 올리지 않고 검색해서 지연 로딩합니다.
  • 실행 계층샌드박스, 타임아웃, 출력 절단. 에러를 예외로 터뜨리지 않고 tool_result로 되돌려 모델이 대응하게 만드는 규약도 여기 삽니다.
  • 권한 게이트allow와 deny 규칙, 사람 승인 인터럽트, 위험 명령 차단.
  • 컨텍스트 예산 관리컴팩션 시점, 오래된 도구 결과 정리, 프롬프트 캐시 경계 배치.
  • 훅PreToolUse에서 특정 호출을 막고 PostToolUse에서 포매터를 돌리는 식으로, 라이프사이클 이벤트에 결정적 코드를 끼웁니다.
  • 서브에이전트 오케스트레이션격리 컨텍스트를 만들고 마지막 메시지만 회수하는 규약, 병렬 실행.
  • 상태와 기억세션 저장과 재개, 메모리 파일, 할 일 목록.
  • 피드백 채널테스트, 린터, 빌드, 스크린샷처럼 모델이 자기 결과를 검증할 신호를 공급하는 배관. 하니스 엔지니어링의 절반은 이 검증 신호 설계입니다.

세 회사의 하니스 전부가 스킬만큼은 같은 오픈 표준(SKILL.md)을 읽습니다. 경로와 멀티에이전트 방식이 다를 뿐입니다.

md 파일만으로 어디까지 가능한가

md로 하는 일은 이미 있는 하니스(Claude Code)를 설정하는 것입니다. 하니스 자체를 새로 만드는 일은 코드의 영역입니다. 그런데 이 설정 표면이 생각보다 깊어서, 서브에이전트 frontmatter의 tools, model, maxTurns만으로 도구 제한, 모델 라우팅, 턴 예산까지 조절됩니다. 경계는 보장입니다. md는 모델에게 주는 조언이라 따를 확률이 높을 뿐 강제가 아니고, 반드시 일어나야 하는 것은 settings.json의 권한과 훅, MCP 서버 코드, SDK의 루프처럼 하니스가 실행하는 층에 둬야 합니다.

판단 기준 한 줄 어겨도 복구되는 규칙은 md에 쓰고, 어기면 사고가 나는 규칙은 settings.json과 훅에 씁니다. 커밋 전 테스트를 CLAUDE.md에 쓰면 대체로 지켜지는 부탁이고, PreToolUse 훅으로 걸면 예외 없는 법이 됩니다.

06정석 셋팅

낮은 층부터 채우는 여덟 단계

원칙은 하나입니다. 통하는 가장 낮은 층에 두고, 필요해질 때만 한 층씩 올립니다.

  1. CLAUDE.md에 사실만 짧게빌드 명령, 컨벤션, 디렉터리 구조. 절차문이 자라기 시작하면 이사 신호입니다.
  2. 자란 절차는 스킬로 추출본문은 SKILL.md에, 긴 자료는 references/에 빼서 읽을 때만 로드되게, 결정적인 단계는 scripts/에 빼서 코드가 컨텍스트에 안 들어가게 합니다.
  3. 부작용 있는 워크플로는 사람 전용으로배포 같은 것은 disable-model-invocation을 걸어 슬래시로만 부릅니다.
  4. 탐색과 병렬 작업은 서브에이전트로도구를 좁히고 경량모델을 지정해 본 대화의 컨텍스트와 비용을 지킵니다.
  5. 외부 시스템은 .mcp.json으로 커밋팀원이 클론하면 같은 연결을 갖게 됩니다.
  6. 보장이 필요한 규칙은 권한과 훅으로차단 목록, 자동 포매팅, 위험 명령 가드가 settings.json에 삽니다.
  7. 검증을 싸게 만들기테스트와 린트 명령을 문서화해 두면 모델이 고치고 스스로 확인하는 피드백 루프가 돌기 시작합니다.
  8. 제품이 에이전트 자체가 되면 SDK로자기 루프와 자기 도구를 코드로 잡되, SDK도 같은 .claude 규약을 읽기 때문에 위에서 쌓은 md 자산이 그대로 이월됩니다.

기본편의 네 가지 요소는 하니스가 사용자에게 열어 둔 설정 표면이고, 하니스 엔지니어링은 그 표면 아래 코드를 직접 잡는 일입니다. /code-review 한 번에 이 층들이 전부 접혀 들어 있습니다.
